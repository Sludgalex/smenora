# Security Policy — SMENORA

## Поддерживаемые версии

В первую очередь исправления безопасности относятся к текущей поддерживаемой линии SMENORA. Исторические релизы «СМЕНАРИУМ» могут сохраняться в GitHub Releases, но не считаются автоматически поддерживаемыми.

## Как сообщить о проблеме

Если проблема не содержит чувствительных данных, создайте GitHub Issue и укажите:

- версию SMENORA;
- версию Windows/Linux;
- тип установки: EXE / исходный запуск / legacy Windows 7;
- краткие шаги воспроизведения;
- ожидаемый и фактический результат;
- обезличенный диагностический материал, если он действительно нужен.

Не публикуйте в Issue:

- рабочий `data.json`;
- ФИО сотрудников;
- реальные табели, сведения об оплате труда и KPI;
- резервные копии;
- Attendance PIN/QR credentials;
- токены, пароли, приватные ключи;
- конфигурацию, содержащую персональные или служебные данные.

Для уязвимостей, которые нельзя безопасно раскрывать публично, используйте закрытый канал связи через официальный сайт проекта: https://smenora.ru/

## Модель безопасности

SMENORA проектируется как локальная система. Основная рабочая база должна оставаться у пользователя.

Подключаемые модули должны использовать только документированные Core API/services и не должны получать произвольный доступ к внутреннему состоянию приложения.

Модульный загрузчик не должен автоматически исполнять неизвестный Python-код из пользовательской папки. На текущем этапе предполагаются только официальные встроенные/подписанные модули SMENORA.

## Локальная защита

Локальная PIN-защита приложения является дополнительным уровнем контроля доступа и не заменяет:

- системную учётную запись Windows/Linux;
- BitLocker/LUKS или иное шифрование диска;
- разграничение прав ОС;
- физическую защиту рабочего места;
- резервное копирование.

## Обновления и миграции

Изменения схемы данных должны выполняться только через контролируемые миграции с резервной копией и обработкой ошибки. Отключение коммерческого модуля не должно автоматически удалять его пользовательские данные.

## Лицензирование

Будущая система лицензирования должна хранить приватный ключ подписи только на серверной стороне/HSM. Клиентская программа должна содержать только публичный ключ проверки и не должна блокировать пользователю доступ к его собственным данным при ошибке лицензии.
